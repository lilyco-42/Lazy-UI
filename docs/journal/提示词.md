# UI 框架设计需求（AI 可读整理版）

## 一、项目定位

构建一个跨平台 UI 框架，融合三种来源的设计思想：

| 来源 | 借鉴内容 |
|---|---|
| [Dear ImGui](https://github.com/ocornut/imgui)（C++） | UI 风格与组件模型，与渲染后端解耦 |
| [Material Design 3](https://m3.material.io/)（Google） | 色彩系统、组件尺寸规范 |
| Kotlin Compose | 自描述式函数参数、声明式 UI 写法（如 `Box(height=100.dp, width=100.dp)`） |

目标：把 imgui 传统的"链式调用"风格，重构为参数自描述、声明式的目标风格，使代码本身即文档。

---

## 二、优先级需求

### P0（必须）
- 实现 imgui 风格的基础组件体系（组件语义与视觉风格参考 imgui，但不依赖具体渲染后端）

### P1（重要）
- 应用 MD3 的色彩体系与合理的 UI 尺寸规范
- 采用 Kotlin Compose 式的声明式、自描述 API 设计

### P2（增强）
- 遵循"约定大于配置"（Convention over Configuration）
- 所有默认组件即为最优实践模板，无需额外配置即可获得最佳效果

---

## 三、核心设计理念

### 3.1 约定大于配置（借鉴 Ruby on Rails 思想）

**原则**：声明一个组件时，框架自动提供以下默认能力，开发者无需关心：
- 跨平台兼容性
- 合适的 UI 尺寸与字体
- 国际化（i18n）

开发者只需绑定"内容"与"行为"这两类最小必要参数。

**示例**：

```
// 有绑定函数：点击后自动调用 a()，组件自动向 a() 传递必要数据
button("启动", a())
fn a() { print("pressed") }

// 无绑定函数：仍是合法组件，框架自动分配唯一 id，可后续按 id 获取/操作
button("hello")
```

要求：默认样式必须符合业界最优 UI 设计规范（即"默认值 = 最佳实践"），而不是留空等待开发者手动配置。

### 3.2 默认组件最优

默认组件已内置解决：
- i18n（国际化）
- 跨平台渲染差异

框架应假设自己是"资深工程师给出的最优默认模板"，开发者写业务 UI 时无需重新决策这些问题。

**示例场景**：

```
main() {
  侧边栏({
    启动()
    设置()
    关于()
  })
  日志面板()
  日志进度条(默认 = nvim dialog 样式)
}
```

对应的模块划分：
- `侧边栏.rs`：实现侧边栏 UI 逻辑
- `侧边栏.toml`：声明该组件的"最常见最优配置"

框架应能从 `.toml` 配置中**自动推断布局关系**，例如：
- 侧边栏与日志面板 → 自动推断为 `flex` 布局
- 日志进度条 → 自动推断固定在底部，占高度 10%

即：布局关系、组件间关系应能从声明式配置中被自动推导，而非手动写死。

## 四、术语说明（供 AI 理解上下文用）

- **imgui**：即时模式 GUI 库（C++），此处仅借鉴其组件风格与交互模型，不涉及具体渲染后端实现。
- **MD3**：Material Design 3，Google 的开源设计系统；此处主要借鉴其色彩规范与组件尺寸标准。
- **Kotlin Compose 风格**：函数参数自带语义、声明式描述 UI 的写法，用于将原本的链式调用 API 改造为可读性更强的目标风格。
- **约定大于配置**：借鉴 Rails 思想，框架提供合理默认值，减少开发者的显式配置负担。
- **默认组件最优**：所有内置组件的默认表现即已是跨平台、i18n、最佳实践下的最优解。

---

## 五、实现要求总结

1. 组件 API 设计需同时满足：imgui 的交互语义 + Compose 式的声明语法。
2. 视觉与尺寸规范对齐 MD3。
3. 每个组件的默认参数即为最佳实践，无需强制配置。
4. 支持通过配置文件（如 `.toml`）描述组件关系，并由框架自动推导布局（如 flex、位置占比等）。
5. 组件即使不绑定回调函数，也应可通过自动生成的 id 被后续引用。
